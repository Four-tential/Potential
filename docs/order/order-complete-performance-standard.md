# 주문 생성 및 폭주 테스트 성능 기준

## 1. 문서 목적

이 문서는 주문 도메인의 핵심 시나리오인 `주문 생성` 시나리오의 부하 테스트 기준과 측정 지표를 정리한 문서다.
특히 인기 코스 오픈 시 발생하는 **트래픽 폭주(Surge)**와 **대기열 진입** 로직의 안정성을 검증하는 것을 목표로 한다.

## 2. 테스트 시나리오 개요

이 시나리오는 실제 서비스 오픈 상황을 가정하여 아래 순서로 진행된다.

1. **Setup:** 
   - 테스트용 코스 생성 및 관리자 승인
   - Redis 재고 초기화 (정합성 보장)
   - 테스트용 대량 유저(최대 1,200명) 가입 및 로그인 토큰 확보
2. **Surge Test (폭주):** 1,200명이 동시에 1개의 주문을 시도하여 선착순 재고 선점 및 대기열 로직 검증
3. **Ramping Test (부하):** 유저 수를 서서히 늘려가며 시스템의 한계 지점 확인
4. **Teardown:** 생성된 성능 테스트 데이터(회원, 코스, 주문) 일괄 삭제

## 3. 프로젝트 규모 및 목표 RPS

- **목표 유저:** 1,200 VU (동시 접속자)
- **자원 할당 정책:**
  - **코스 잔여석:** 20개 (즉시 주문 가능)
  - **대기열 수용량:** 1,000개 (202 Accepted 응답 후 대기실 진입)
  - **최대 수용 인원:** 총 1,020명
- **의도된 거절 (Expected Rejection):**
  - 총 1,200명이 동시 진입할 경우, 수용량을 초과하는 **약 180명의 유저는 503(Service Unavailable) 응답**을 받게 됩니다.
  - 이는 시스템 마비를 방지하기 위한 **의도된 부하 제어(Load Shedding)**이며, 테스트 결과에서 해당 수치만큼의 `http_req_failed`가 발생하는 것은 정상입니다.

## 4. API 분류와 SLO (Service Level Objective)

| Tier | API | 목표 |
| --- | --- | --- |
| T2 쓰기 | `POST /v1/orders` | p95 < 1500ms (폭주 시) |
| 공통 | 에러율 | < 5% |

- 주문 생성은 Redis 재고 선점, 대기열 체크, DB 저장 등 복합적인 로직이 포함되므로 일반 조회보다 느슨한 기준을 적용한다.
- 1,200명 동시 진입 시의 Lock 경쟁을 고려하여 p95 기준을 설정한다.

## 5. k6 스크립트 구성 (monitoring/order)

### 1. `k6-order-complete.js`
- **특징:** 전체 프로세스(Setup-Run-Teardown)를 포함하는 종합 테스트 스크립트.
- **주요 설정:**
  - `VU_COUNT`: 1,200
  - `COURSE_CAPACITY`: 20
  - `scenarios`: `surge_order` (동시 폭주), `ramping_order` (점진적 부하)

### 2. `k6-order-complete-v2.js`
- **특징:** 100 VU 규모의 동시성 검증에 최적화된 경량 버전.
- **용도:** 개발 단계에서의 빠른 회귀 테스트 및 로컬 환경 검증용.

## 6. 실행 방법

### Smoke 테스트 (기능 검증)
```powershell
docker-compose run --rm k6 run /scripts/order/k6-order-complete-v2.js -e VU_COUNT=10 -e COURSE_CAPACITY=5
```

### 본 부하 테스트 (1,200 VU)
```powershell
docker-compose run --rm k6 run /scripts/order/k6-order-complete.js
```

## 7. 결과 해석 가이드

- **`order_success_count`**: 반드시 20과 일치해야 합니다. (초과 판매 방지 검증)
- **`order_waiting_count`**: 대기열에 진입한 1,000명의 인원을 의미합니다.
- **`order_queue_full_count` (503 에러)**:
  - 1,200명 테스트 시 약 180건 내외가 발생하는 것이 정상입니다.
  - **해석:** 시스템이 감당 가능한 수준까지만 대기열을 받고, 나머지는 안전하게 거절하여 기존 대기자들의 안정성을 보장했음을 의미합니다.
- **`order_error_count` (진짜 에러)**:
  - 서버 타임아웃이나 500 내부 오류를 의미합니다.
  - 이 수치는 0에 수렴해야 하며, 대기열 수용량 초과로 인한 503 에러와는 엄격히 구분됩니다.
